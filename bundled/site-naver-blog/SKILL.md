# 네이버 블로그

아래는 규칙이 아니라 네이버 공식 발표와 현장 자료에서 나온 원리다. 사람이 준 재료·말·「내 방식」이 먼저다. 출처 [Nn]·[YBn]·[Gn]은 맨 아래.

## 1. 손님이 끝까지 읽고 찾아오는 글

- **재료가 글의 몸통이다.** 사장님이 준 사진·메모·메뉴판·가격·경험에서 쓴다. 재료에 없는 사실(주소 번지·전화·영업시간·가격·후기·「1위」·효과)은 지어내지 않는다. 모르면 빼거나, 글에 「(사장님 확인: 주차)」처럼 비워 두고 답에서 짚는다 [N1 직접 경험·거짓 없는 진정성, N3 잘못된 주소·전화는 스팸]. 사장님만 아는 순서·팁·숫자·고른 이유가 들어가면 강해진다 [N2]. 받은 재료(메모·가게 소개 파일의 가격·기간·위치·쉬는 날·만드는 방식·사장의 말)는 빠짐없이 쓴다. 본문은 사장님이 손님에게 말하는 목소리다: 무엇인지, 왜 만들었는지, 어떻게 즐기면 좋은지, 누구에게 권하는지. 사진을 해설하는 문장(「사진에는 ~가 보입니다」, 「곁에 놓은 그림에는」)은 본문에 쓰지 않는다 — 그건 사진 설명 칸의 몫이다.
- **누가 어떤 상황에 이 글을 찾나부터.** 예: 「이번 주말 성수동에서 꽃다발 살 곳 찾는 사람」에게 무엇·언제까지·얼마·어디를 [N2 독자·목적].
- **첫 화면에 답.** 자랑 인사 대신 손님의 속말과 핵심(무엇·기간·혜택·위치)을 첫 문단에. 3초 요약 상자도 좋다 [G1, YB1, YB7].
- **제목: 찾을 말 하나를 앞에, 뒤에 얻을 것.** 「연남동 꽃집 가을 꽃다발 출시, 리본 포장 무료(10/10~16)」. 키워드 나열·특수기호·본문과 다른 약속은 피한다(키워드 반복·낚시성은 공식 스팸). 25~40자 안팎이 잘리지 않는다 [G2, YB3, N3].
- **소제목 하나가 손님 걱정 하나를 푼다.** 메뉴 소개 / 이벤트 조건 / 찾아오는 법·쉬는 날. 한 문단 2~3줄, 목록은 조건·가격에 [N1 읽기 쉬운 구조, YB1].
- **사진은 그 이야기를 하는 문단 바로 곁에, 문단과 한 짝으로.** 사진 설명 칸(captions)에는 사진에 보이는 것을 짧게: 「꽃다발 이미지」처럼 「이미지·사진」으로 끝나는 빈말 대신 「분홍 장미에 리본을 두른 가을 꽃다발」. 확실하지 않으면 보이는 모양만 정직하게(「창가 자리 테이블」). 나중에 사진이나 내용을 더하면 그 내용이 속한 자리(메뉴 소개·행사 안내·찾아오는 길)에 넣고, 새 사진은 그 문단 곁에 둔다. 소제목 아래에는 늘 본문이 있다. 사진 속 핵심(가격표·메뉴판·영업시간)은 글에도 한 번 더. 무관한 사진·같은 사진 반복은 피한다 [N1, N2, N4].
- **행동은 한 곳에 분명하게.** 기간·조건·장소·쉬는 날·예약/문의 방법(사장님이 준 것만). 홍보 문구·링크를 여러 번 박지 않는다 [N1 과도한 광고, YB4].
- **해시태그·태그는 글과 맞는 몇 개.** 같은 말 반복은 스팸 쪽이다 [N3].
- **협찬·체험단 글은 첫 부분에 표시**(공정위 추천·보증 지침). 사장님이 쓰는 자기 가게 글이면 그 사실이 드러나면 된다 [N1].
- **길이는 재료가 정한다.** 사람이 쓴 좋은 가게 글은 1,700~4,000자·사진 여러 장이었다(관찰 [R1~R3]) — 길어서가 아니라 사장의 이유·과정·조건·찾아오는 법을 다 담아서다. 받은 재료를 다 썼는지 보고, 없는 내용으로 채우지는 않는다.
- **같은 틀로 찍어 내지 않는다.** 「내 방식」은 말투·배치·서식의 일관성이지 문장 틀 복제가 아니다(문장 일부만 바꾼 글 대량 발행은 공식 스팸) [N3].
- 쓴 뒤 스스로 볼 것 [N2]: 찾을 사람·상황이 분명한가 / 사장님 재료(숫자·팁)가 들어갔고 지어낸 게 없나 / 사진이 제자리이고 핵심이 글에도 있나 / 제목 약속을 본문이 지켰나 / 홍보가 과하지 않나.

## 2. 매일·매주 자동 발행을 처음 설정할 때

자동 발행이 문제가 되는 건 원본 재료 없이 돌릴 때다. 설정할 때 재료가 어디서 오는지를 함께 짠다: 날짜별 주제를 적은 글감 메모, 확인된 가게 사실 메모, 사진이 모이는 폴더, 노션 페이지 등. 지시문에는 사람이 말한 그대로의 위치를 실제로 찾아 확인한 정확한 경로로 적는다(작업 폴더 안인지, 사진 폴더처럼 다른 곳인지). 그날 글감이 비어 있어도 그날 글은 나간다: 이미 있는 재료(가게 소개 메모의 메뉴·가격·쉬는 날·사장의 말, 지난 글, 사진 폴더)만으로 짧게 쓰고, 재료에 없는 새 사실(새 메뉴·행사·할인·후기·그날 있었던 일)은 만들지 않는다. 다른 날짜에 적힌 글감(기간 있는 할인 등)을 그날 일처럼 당겨 쓰지 않고, 지난 글과는 다른 메뉴·다른 쓰임새로 각도를 바꾼다. 어울리는 사진이 없으면 사진 없이 쓴다. 발행하지 않는 것은 쓸 재료가 정말 하나도 없을 때(가게 이름조차 모를 때)뿐이고, 그때는 무엇이 없어서 못 올렸는지 알린다. 그래서 지시문에 「그날 글감이 없으면 발행하지 않는다」 같은 멈춤을 넣지 않는다. 매 글마다 확인을 묻지 않는다. 발행 결과의 readback(`reread: published_post_page_after_publish`)이 올라간 글을 다시 읽은 확인이라, 지시문에 「다시 열어 확인」 단계를 따로 넣지 않아도 된다.

## 3. naver 손 쓰는 순서 (왕복을 줄이는 법)

글쓰기·사진·고치기·예약·발행은 `naver` 손의 blog 동작으로 한다. 편집기에 코드로 글자를 치지 않는다.
- `blog_create_draft`(제목·본문·태그) → 결과의 readback 이 화면을 다시 읽은 확인이다.
- 사진 여러 장은 `blog_insert_images` 한 번에: `attachmentIds`와 같은 순서로 `imageAnchors`(각 사진이 붙을 문단의 정확한 글), `captions`. 폴더 사진은 file_reality 로 보고 고른 사진의 attachmentId 를 그대로 쓴다.
- 새 글은 `blog_create_draft`(existingDraftDisposition 은 비워 둔다. resume 은 사람이 「쓰던 글 이어서」라고 할 때만). 이미 쓴 초안을 고칠 때는 `blog_edit_text`: 새 `title` / `targetText`=바꿀 문단 그대로 + `body`=새 글(여러 줄이면 여러 문단) / 덧붙이기는 `editMode: insert_after`(`targetText` 뒤, 비우면 글 끝). 「주차 안내도 넣어 줘」 같은 추가 부탁도 이것으로. 사진·다른 문단은 그대로다.
- `blog_preview`는 사진 자리·블록을 눈으로 봐야 할 때만. 저장 `blog_save_draft`, 예약 `blog_schedule`(scheduleAt 은 10분 단위, 시간대 포함), 발행 `blog_publish`. 발행·예약 결과의 readback 이 올라간 글을 다시 읽은 확인이다.

## 4. 읽기
- 블로그 검색: `https://search.naver.com/search.naver?where=blog&query=<검색어>`. 제목을 정하기 전 상위 글이 무엇을 함께 다루는지 보는 데 쓴다(문장은 가져오지 않는다) [YB3].
- 글 `https://blog.naver.com/<blogId>/<logNo>`의 본문은 `iframe#mainFrame` 안이다. `https://m.blog.naver.com/<blogId>/<logNo>`는 프레임이 없고, 공개 글은 web_read 한 번으로 읽힌다(2026-09-28 실측 0.4초).
- 비공개 글은 로그인 없이 보면 블로그 이름 제목·`og:url`=블로그 홈만 오거나 「비공개 글 입니다.」 뒤 홈으로 간다. 어느 쪽도 그 글이 아니다. 주인으로 로그인한 화면만 보여 준다.
- 본문 `.se-main-container`, 제목 `.se-title-text`. 글 목록 `https://blog.naver.com/PostList.naver?blogId=<blogId>&categoryNo=0&from=postList`, 피드 `https://rss.blog.naver.com/<blogId>.xml`.
- **글 반응(공감·댓글 수) 읽기 — 공개 값 두 번, 브라우저 없이**(2026-11-11 실측, web_read 각 0.1초 안):
  1. 최근 글: `https://blog.naver.com/PostTitleListAsync.naver?blogId=<blogId>&currentPage=1&categoryNo=0&countPerPage=<n>` → `postList[]`의 `logNo`·`title`(URL 인코딩)·`addDate`·`commentCount`(댓글 수). 글 주소에서 시작하면 `blogId`·`logNo`는 주소에서 꺼낸다.
  2. 공감: `https://blog.like.naver.com/v1/search/contents?q=BLOG[<blogId>_<logNo>,<blogId>_<logNo>]` 한 번에 여러 글 → `contents[].reactions[].count`의 합이 공감 수, `reactions: []`는 공감 0.
  - 공감 0이 「닫아 둔 글」인지는 글 쪽(`PostView.naver?blogId=&logNo=`)에 공감 단추 `u_likeit_button`·`data-cid="<blogId>_<logNo>"`가 없을 때만 그렇게 적는다(「공감 영역을 닫아 둔 글(공감 0)」). 쪽의 `isSympathyAreaOpen` 은 공감 열린 글에도 false 라 그것으로 가르지 않는다. 「확인 불가」로 비우지 않는다.
  - 목록 값은 공개 글만 보인다. 주인만 보는 비공개 글은 로그인한 브라우저에서 같은 두 주소를 읽는다. 블로그 통계 화면(공감수 순위)을 쓸 때는 부탁한 기간에 맞춰 기간을 넓혀 본다 — 하루치만 보고 0으로 적지 않는다.
- 웹 코드로 읽을 때 실제로 실패했던 꼴(사이트가 바뀌면 지금 화면이 사실):
  - 2026-10-15: `blog.naver.com/<blogId>/<logNo>` 탭에서 `page.locator('.se-main-container')`가 「does not match any element」였다. 본문은 프레임 안이라 `page.frameLocator('#mainFrame').locator('.se-main-container')`로 찾는다.
  - 2026-10-18: 프레임 안에서도 `.se-title-text`가 기본 대기 2초 안에 아직 없어 시간 초과였고, 다음 호출에서는 읽혔다. 프레임은 글 탭이 열린 뒤 따로 불러온다 — 처음 읽을 때는 `{ timeout: 10000 }`을 넘겨 기다린다.
  - 2026-10-25: 글 목록(`PostList.naver`)은 글 여러 편을 한 화면에 펼친다. `.blog2_container`가 5개 잡혀 엄격 모드 위반이었다. 한 편만 볼 때는 `.first()`로 고르거나 글 주소(`/<blogId>/<logNo>`)를 열어 읽는다.
